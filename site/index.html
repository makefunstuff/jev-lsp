Language server · decision model

Steer code with rules, not with token maxxing.

Jev is a classifier, not a chat model. A rule asks one typed question about one line. Jev answers with a value and a probability — never prose.

jev-lsp runs those rules while you edit (or while a harness writes), and reports through normal editor surfaces: diagnostics, code actions, code lens.

GitHub README

Heavily WIP. Interface and config may change; nothing here should be relied on yet.

What Jev is

  • One question → one answer. Not a review essay. A pass/fail (or typed value) with a probability floor.
  • Rules live in the repo. Your words + a pattern that names candidate lines, versioned like code.
  • Semi-deterministic. Pattern is exact; judgement clears the rule’s own floor before anything publishes.

How the loop works

  1. Spec. Write what the code has to do.
  2. Rules. Turn that into .jev/rules/*.json.
  3. Steer. jev-lsp applies them on save — to you or to a harness — on the line.
  4. Stay on track. Findings are ordinary diagnostics a client already knows how to read.

Why local / cheap models work here

Well-defined rules carry the project conventions. The model does not re-read your whole style guide every turn — it answers about one candidate line.

Measured on this project (rules pass vs chat review of the same file): the decide pass is roughly an order of magnitude cheaper, and a save with no matching pattern makes no model call at all.

That is the point of the PoC: accuracy from steering, not from burning tokens.

Clients

Standard LSP only — no custom jev/… methods. Neovim is the primary client; anything that can start a language server can use it (harnesses included). Cursor has an extension under editors/cursor/.
