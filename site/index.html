Documentation, and the case for using it

A language server that checks your code against rules your repository states.

Jev is a classifier, not a chat model. A rule asks one typed question about one line, and Jev answers with a value and a probability, never prose. The rule is your own words plus a deterministic pattern that names the exact lines, so the pattern is exact and the judgement is a probability that has to clear the rule's own floor before anything is published. That is what makes a rule semi-deterministic.

Jev-lsp runs that pass over the files you have open and reports through your editor's own surfaces: diagnostics, code actions, code lens. The ambient pass is the rules in .jev/rules/*.json, applied on save, in whatever client you work in. Standard LSP surfaces only, so any client that can start a language server can use it. Neovim is the primary client.

Proof of concept

The interface, the contract and the configuration keys may change without notice, and nothing here should be relied on yet. The repository's front page says the same thing, about itself:

Heavily work in progress. The interface, the contract and the configuration keys may change without notice; nothing here should be relied on yet.

Shape
One server, standard surfaces: textDocument/diagnostic, codeAction, codeLens, workspace/executeCommand. No custom jev/… methods.
Ambient pass
The repository's rules. With no rule files the pass publishes nothing and reports no_rules.
Decision tier
One question per candidate line, answered with a value and a probability. The chat tiers behind actions, plans and explanations are separate and on demand.
Measured cost
$0.00022 for the rules pass over crates/jev-lsp/src/server.rs (2.6k lines), against $0.00306 for a chat review of the same file.

What it is not. It does not know your spec unless a rule carries it. It answers the question in the rule and nothing else. It is not a correctness oracle, and state = "ready" means the contract passed rather than the file still compiles. A document with text is its unit, so a file has to exist: greenfield work with no file to point at is served by the shell, not by an editor.

01 · The loop

Spec, rules, steering

The workflow the rules carry, quoted from the front page of the repository:

  1. Plan or spec. You, with coworkers or an LLM, write down what the code has to do.
  2. Rules. Turn that spec into .jev/rules/*.json: in the repository, under version control, reviewed like code.
  3. Steering. Jev-lsp applies the rules while you edit by hand, or while a harness generates code, so the findings arrive where the code is: on the line, in the client you already use.
  4. On track. The codebase keeps matching the requirements, and a harness that reads diagnostics picks the steering up.

A person or an agent can do that review by hand. Jev-lsp moves it into the loop: every save, every file, in whatever client you work in. The finding arrives as a diagnostic the client pulls, with the code action and the code lens beside it. No popup, no sound.

A rule is a pattern, a question and a floor

The pattern names candidate lines and decides nothing. The question is what the decision tier is asked about each candidate. min_probability is the floor a true answer must clear before anything is published, and a false answer stays invisible. The finding that reaches the editor carries the rule's title, its prose and the reason the judgement gave:

.jev/rules/no-unwrap-outside-tests.json three fields of the rule 
"inspection": { "kind": "regex", "pattern": "\\.unwrap\\(\\)" },
"judgement":  { "question": "Is this unwrap on a path that ships…",
                "min_probability": 0.85 }

The pattern is why the cost does not grow with the file. It names the lines worth asking about, so a 2.6k-line document costs 5,341 tokens in rather than the 30,562 a review of the same file cost. The measured tables are below.

With no rules there are no ambient findings, and the pass reports no_rules rather than a clean file. The chat review does not step in to cover the gap; that is a decision recorded in PROTOCOL.md §12, not an omission. A save where no rule's pattern matches makes no model call at all.

02 · Use cases

Six rules, and what they answered

Three of the twenty-one rules this repository states about itself, then three rules from docs/TUTORIAL.md with the answers the decision tier gave them. The rule documents are quoted as they are stored.

The check is the repository's own prose

docs/STYLE.md states the register for every document here and ships the audit that enforces it. The rule below is that audit as data: the same regex, and one question that decides whether a hit is a quotation, a banned example or a hedge. The files it claims are this repository's own prose.

.jev/rules/words-must-carry-a-fact.json verbatim 
{ "schema": "jev.rules/1",
  "rules": [
    { "id": "words-must-carry-a-fact",
      "title": "A word must carry a fact, not a temperature",
      "text": "The register bans the words that cannot be checked \u2014 powerful, seamless, robust, simple, easy, effortless, just, very, mostly \u2014 because a reader can neither verify nor act on them; a sentence that needs one has not said what it means.",
      "severity": "warning",
      "applies_to": [
        "**/README.md",
        "**/STATUS.md",
        "**/PROTOCOL.md",
        "**/docs/**/*.md"
      ],
      "inspection": {
        "kind": "regex",
        "pattern": "(?i)\\b(powerful|simple|simply|seamless|robust|delightful|easy|easily|effortless|just|mostly|quite|very)\\b"
      },
      "judgement": {
        "question": "Does this line use a banned word in its own voice, rather than quoting it as an example or using it for a specific fact?",
        "criteria": {
          "true": "the document itself uses the word as a hedge or a temperature",
          "false": "it is quoted as a banned example, or it names a measurement, or it means only (`just` the cursor's line)"
        },
        "min_probability": 0.8
      },
      "verb_hint": "docs"
    }
  ]
}

The criteria pair is where the work happens. The paragraph in docs/STYLE.md that bans those words contains most of them, and a pattern on its own would report it. The false side is what a regex cannot state: a quoted example, a named measurement, and just used to mean only.

A convention, with the answer measured

The pattern finds every .unwrap() in the file and cannot tell a test helper from a handler. The question is what separates them, and the answers were measured against hosted Jev (typesafe/jev-1.13): an unwrap on a request-reachable path answered 0.85–0.91 across runs, and the same call inside #[cfg(test)] answered 0.05 on 15 of 15 runs. The criteria states the same split in the rule, and the criterion is what carries the decision.

.jev/rules/no-unwrap-outside-tests.json verbatim 
{ "schema": "jev.rules/1",
  "rules": [
    { "id": "no-unwrap-outside-tests",
      "title": "Unwrap outside tests",
      "text": "A `.unwrap()` outside test code is a defect: the value was not checked, and a failed check takes the process down instead of the request \u2014 handle the error, or say in a comment why it cannot fail.",
      "severity": "warning",
      "applies_to": [
        "**/crates/**/*.rs"
      ],
      "inspection": {
        "kind": "regex",
        "pattern": "\\.unwrap\\(\\)"
      },
      "judgement": {
        "question": "Is this unwrap on a path that ships and can reach a value it did not check, rather than inside a test module, a doc comment, or behind an invariant the surrounding code states?",
        "criteria": {
          "true": "code that ships can reach it and the value is not guaranteed",
          "false": "it is in a test module, quoted in a doc comment, or behind an invariant the surrounding lines state"
        },
        "min_probability": 0.85
      },
      "verb_hint": "fix"
    }
  ]
}

The floor is not a free parameter. At the 0.75 that this rule first shipped with, 4 of 15 runs published one of its two lines and not the other, from answers sitting in a 0.75–0.79 band. It ships 0.85 now, where none of 15 runs published either line, and the fixture that must fire answered 0.97–0.98 on 15 of 15 runs at both floors. Over this repository's own crates/**/*.rs, this rule accounted for both findings of the sweep: one line of crates/jev-lsp/src/server.rs. Sources: docs/GUIDE.md §4 and docs/VERIFICATION.md §8.

One rule, four kinds of harness file

|| true and an empty except turn a broken run into a green one, and the log reader cannot tell the two apart. The pattern names that shape in Python, in shell and in the workflow files, so one rule covers the harnesses a result has to be trusted from. The floor is 0.7 because the question has to separate a discarded failure from cleanup whose failure cannot change the result.

.jev/rules/no-swallowed-failures.json verbatim, text and criteria trimmed to their first sentence 
{ "schema": "jev.rules/1",
  "rules": [
    { "id": "no-swallowed-failures",
      "title": "A failure the caller needed is not swallowed",
      "severity": "warning",
      "applies_to": [
        "**/verify/**/*.py",
        "**/verify/**/*.sh",
        "**/verify/**/*.lua",
        "**/scripts/**/*.sh",
        "**/.github/workflows/*.yml"
      ],
      "inspection": {
        "kind": "regex",
        "pattern": "\\|\\|\\s*true\\b|except[^:]*:\\s*(pass|break|continue)\\b"
      },
      "judgement": {
        "question": "Does this hide a failure the caller or the log needed to see, rather than a best-effort step whose failure cannot matter?",
        "min_probability": 0.7
      },
      "verb_hint": "fix"
    }
  ]
}

The full document carries a criteria pair and a text that states why: a best-effort step that may fail says so where it fails. It is the only rule of the twenty-one that spans languages, because the shape it names appears in all of them.

A sentence from the spec becomes one question

Take a line from the spec, every public function documents the errors and empty values a caller must handle, and turn it into a pattern plus one question. Measured on three public functions, the answers were 0.80, 0.78 and 0.78, and all three published.

The question has to state the violation, because a true answer is what publishes. Phrased as the property you want, does this function document its returns?, the same rule answered false for all three functions at every floor, 0.6 and 0.0 alike, and published nothing. Rephrased as the defect, does this function leave a caller unable to know what it can return?, it answered as above. A false answer is invisible through :Jev inspect, which publishes only what clears the floor, so a backwards question looks exactly like a rule that never fires.

Code a model wrote, and the honest reading of a coarse question

A comment that narrates the next line is the shape of machine-written slop, and the rule that fires on it is the argument for putting the review in the loop. Measured on three comments, it answered 0.65 (# Increment the counter for each frame., a narration), 0.67 (# The upstream API returns 429 with no Retry-After, so back off by hand., which explains why and is a false positive at this floor) and 0.64 (# Return the parsed body., a narration). All three sit inside a 0.03 band, so no floor separates the narration from the explanation. The pattern is right and the question is too coarse, which is a rule to sharpen rather than a floor to move.

That measurement is kept rather than replaced by a conclusion. A rule whose answers straddle the floor is visible here as exactly that.

A harness that reads diagnostics

An agent that generates code reads diagnostics, so the same rule steers the generation as it steers an edit. verify/omp_lsp.sh drives jev-lsp from OMP, a client nobody here wrote, and asserts three things: that the finding reaches the agent's own diagnostics carrying the rule's title, the judgement that followed the rule's prose, the line, the finding id and the rule's severity; that jev.inspect answers through OMP's tool surface with the same finding, its counts and its skips; and that the same fixture with no .jev/rules/ produces no jev diagnostic and an inspect that says no_rules, so a green run cannot be the harness finding something else. An unavailable client is a skip with the reason, never a false pass.

03 · Cost

What a pass costs

A review re-reads the file. A decision answers about the lines a pattern named, so the cost of the pass follows the candidates rather than the file. Everything below was measured on 2026-09-20: the rules pass with jev inspect --force against the hosted decide tier (https://opencode.ai/zen/v1, wire system_one, model jev-1.13), and the review with jev review against a real chat tier (google/gemini-2.5-flash-lite through OpenRouter).

The other ten documents had no candidate and cost nothing, because a save where no rule's pattern matches makes no call at all. That works out at $0.00011 per document and $0.00017 per document that called, 4,124 tokens in and 192 out per calling document. The scale is the candidate count: the largest calling document (21 candidates) cost 6,859 in / 571 out, and a 6-line fixture with one candidate costs 482 in / 29 out.

Where the rates come from

The decide tier's price is the OpenRouter decisions route's own usage.cost, measured at $0.000013776 for 349 tokens, which is $0.0395 per million; an earlier measurement of $0.00002121 for 532 tokens agrees at $0.0399. The Zen route carries usage but no price field, which is why the rate comes from the other route. The chat tier's own cost_details gave $0.10 per million in and $0.40 per million out.

A local decide tier costs nothing per call: measured on this machine over 18 decisions, p50 583 ms and $0.000000 per decision, against $0.000015 per decision for typesafe/jev-1.13 through OpenRouter at p50 591 ms. The latency is comparable; the price is not.

What the numbers do not include

  • The generation itself. The code your harness writes is untouched; what changes is what steering and review cost.
  • The chat tiers, which answer actions, plans and explanations, stay the expensive path and are on demand.
  • No local decide tier has been run end to end here. The recipe, the price and the latency are measured; the wiring is not, and no local harness generation run has been measured on this machine.
  • Local is cheap per token, not fast. This machine generates at 33 tok/s on a small MoE (96 tokens in 2.9 s), its serving logs for the larger code models sit at ~1.5–2 tok/s, and the project's own local soak measured a 35B at 5.7–12.4 s per ambient review and 7.3–15.5 s per resolve. A model that slow becomes viable when the tokens it has to produce drop, which is what a rule set does.
  • Accuracy is not the same across routes. The same 18 decisions answered 12/18, 67% on the local arm against 17/18, 94% for typesafe/jev-1.13, so a local tier has less margin and the floor wants more room.
  • The instruction document, as arithmetic rather than a measurement: a 2,000-token instruction file re-sent across 50 turns is about 100,000 instruction tokens in one session, $0.010 at the measured chat rate.

What leaves the machine

The chat tiers default to a local OpenAI-compatible server. The decide tier's default is remote: wire = "system_one", base_url = "https://api.typesafe.ai/v1", model jev-latest, key from TYPESAFE_API_KEY. On a default install the text of a changed file leaves the machine on every rules pass, on save, without anything being asked for. Two settings change that, and either one is a line of configuration:

settings.json docs/MODEL.md §8 
// a local System One server: the same wire, on your machine
{ "models": { "decide": { "base_url": "http://127.0.0.1:8009/v1", "model": "kev-latest" } } }

// or no ambient pass at all: the rules pass is the only ambient path
{ "rules": { "enabled": false } }

JEV_DECIDE_BASE_URL, JEV_DECIDE_MODEL, JEV_DECIDE_WIRE and JEV_DECIDE_TIMEOUT_MS do the same from the environment. JEV_BASE_URL does not move this tier: it names an OpenAI-compatible chat server, and a decision is not a chat. Turning the rules off returns the ambient path to the review tier, which is also remote by default.

04 · Install

Three clients

There is no release page yet, so the two binaries come from cargo install, which needs a Rust toolchain (1.75 or later). git clone plus cargo build --release produces the same two binaries under target/release/.

shell the two binaries 
$ cargo install --git https://github.com/makefunstuff/jev-lsp --locked jev-lsp jev

That puts jev-lsp (the server) and jev (a CLI) in ~/.cargo/bin, which is on PATH for a normal toolchain install. cargo binstall, a Homebrew formula and a published .vsix do not exist yet.

Neovim, the primary client

The plugin owns the attach pass that covers files Neovim cannot identify, the keymaps and :Jev. Point a plugin manager at the repository's nvim/ directory, or symlink it, then call setup() from your config.

shell, then init.lua docs/TUTORIAL.md §1 
# 1. the plugin
ln -s /path/to/jev-lsp/nvim ~/.local/share/nvim/site/pack/jev/start/jev

-- 2. in your config; with `jev-lsp` on PATH, the command is the plugin's own default
require('jev').setup({})

setup() registers the client config, calls vim.lsp.enable('jev') and starts the attach pass. Nothing appears on screen yet. A lazy-managed config takes the same plugin as a local dir spec. Without the plugin, Neovim's own client reaches the same surfaces in two lines, and filetypes is then the client's job.

Four keys cover the surfaces; everything else is typed, and :Jev <Tab> completes eighteen subcommands.

Source: the front page of README.md and docs/GUIDE.md §1. The plugin requires Neovim ≥ 0.12.
key what it does
<leader>ja the code-action picker; in visual mode the selection is the scope
<leader>ju undo the last applied edit; the buffer returns to before it, byte for byte
<leader>jq ask a question about the file; the answer opens in a scratch buffer
<leader>js status: queue, budgets, endpoints in force

:Jev inspect reports what the rules pass did for the current file: the counts, the findings and every skip, so a pass that found nothing can be told apart from a pass that never ran.

Any LSP client, including a harness

jev-lsp --stdio is a language server, so any client that can start one can use it. The plugin is optional: without it you still get findings through pull diagnostics and workspace/diagnostic/refresh, edits through codeAction and codeAction/resolve, and every command through workspace/executeCommand, including jev.inspect. The server reads its endpoints from the environment it is started with.

OMP, the client the recorded transcript at the top of this page comes from, takes a JSON entry written to <project>/.omp/lsp.json, or to ~/.omp/agent/lsp.json to apply it to every project:

.omp/lsp.json README.md, “Use it with another LSP client” 
{"servers":{"jev-lsp":{"command":"/path/to/jev-lsp/target/release/jev-lsp","args":["--stdio"],
  "fileTypes":[".rs",".py",".md",".toml",".json",".lua",".sh"],"rootMarkers":[".git"],
  "settings":{"jev":{"models":{"decide":{"wire":"system_one",
    "base_url":"https://opencode.ai/zen/v1",
    "model":"jev-1.13", "api_key_env":"TYPESAFE_API_KEY",
    "timeout_ms":15000}}}}}}}

OMP answers the server's workspace/configuration pull with settings.jev, so the entry can carry the endpoints. settings names the key's variable (api_key_env) and cannot carry the key itself, so export it before the harness starts; without it a hosted decision call fails with model_error. Environment variables win over the settings block, which is what lets the stub and local-server recipes work without editing the client config.

Cursor

/Applications/Cursor.app/Contents/Resources/app/bin/cursor --install-extension /tmp/jev-0.1.0.vsix

The decide endpoint

Nothing is published until the decision tier answers. It is hosted Jev by default (api.typesafe.ai, model jev-latest), and it needs a key. The other routes, and the wire and timeout_ms traps that go with them, are in docs/MODEL.md §8.

shell the key, and a second route 
export TYPESAFE_API_KEY=…

# a hosted route that is not the default needs the wire, the ceiling and the key's name
export JEV_DECIDE_WIRE=system_one
export JEV_DECIDE_BASE_URL=https://opencode.ai/zen/v1
export JEV_DECIDE_MODEL=jev-1.13            # not jev-1.13-free: 429 FreeUsageLimitError in bursts
export JEV_DECIDE_TIMEOUT_MS=15000          # the 5000 ms default is too close to its tail
export JEV_DECIDE_API_KEY_ENV=OPENCODE_API_KEY
export OPENCODE_API_KEY=<key>

The chat tiers answer actions, plans and explanations rather than findings, and are needed only for those. api_key_env names a variable and never carries a key; prompt text and response bodies are never persisted outside the conclusion cache, which stores parsed conclusions rather than raw model traffic.

The first rule

.jev/rules/ is read from the repository root, in path order. With a file a rule claims in a buffer, :Jev inspect reports what the pass did, and the next save puts the sign in the margin by itself.

shell, then Neovim docs/TUTORIAL.md §3 
mkdir -p .jev/rules
cat > .jev/rules/handlers.json <<'JSON'
{ "schema": "jev.rules/1",
  "rules": [
    { "id": "no-unwrap-in-handlers",
      "title": "Unwrap in a request handler",
      "text": "A handler must not unwrap: a bad request would take the worker down. Return the error instead.",
      "severity": "warning",
      "applies_to": ["src/**/*.rs"],
      "inspection": { "kind": "regex", "pattern": "\\.unwrap\\(\\)" },
      "judgement": {
        "question": "Is this unwrap reachable from a request handler, rather than from test or startup code?",
        "criteria": { "true": "a request can reach it", "false": "test or startup code" },
        "min_probability": 0.75 },
      "verb_hint": "fix" } ] }
JSON

# then, with a file it claims in a buffer
:Jev inspect     " what the pass did: rules considered, candidates found, findings, every skip
:w               " and on the next save the sign appears by itself

Three things cost an hour if they are not known. Editing a rule does not repaint the findings already on screen, because nothing watches .jev/rules/; :Jev inspect --force or :Jev recompute apply it now. A pass that found nothing says so, listing unchanged, no_rules, and any rule file that failed to load with its reason. And a broken rule file does not take the pass down: a file that cannot be read or parsed, or that carries another schema, is skipped with a reason and the rest still load.

05 · Writing rules

The rule document

A rule pairs a convention in prose with the inspection that finds the lines it is about. .jev/rules/ is read from the repository root, in path order, and every file carries "schema": "jev.rules/1". What each field decides, in the order a rule author cares about them:

Source: docs/GUIDE.md §4.
field what it decides
applies_to globs over the document's path relative to the workspace root (the absolute path when there is no root), so src/**/*.rs matches a file at the root's src/, and a leading **/ is optional. A rule for **/*.rs never sees a Python file
inspection.kind regex (every matching line) or absent (the file is expected to contain the pattern and does not: a licence header, a module declaration)
inspection.pattern the candidate finder. It decides nothing: it names lines
judgement.question what the decision tier is asked about each candidate
judgement.criteria passed through to the decision wire unchanged; this question kind wants {"true": …, "false": …}
judgement.min_probability the floor a true must clear. Default 0.5, and it belongs outside the answer's measured spread rather than on it
title, text the finding's label (clipped at 60 characters) and its detail
verb_hint the verb the menu offers first for it: fix, harden, types, docs, rewrite, test, generate

Two things decide whether a rule works

Both were measured against hosted Jev (typesafe/jev-1.13), and both are cheap to get wrong.

The question has to state the violation. A true answer is what publishes, so true must mean the code is wrong. Ask about the decision (is this unwrap reachable from a handler?) and the answer separates the cases; ask about the syntax the regex already matched and the rule says nothing new. A false answer is invisible through :Jev inspect, which publishes only what clears the floor, so a backwards question looks exactly like a rule that never fires.

The floor goes outside the measured spread, not on it. A sharply-posed question answered 0.96–0.97 across 25 real runs (median 0.97, sd 0.0048). The same endpoint on a question nearer the decision boundary varied 0.82–0.86 across 8 runs. A floor at the answer's median turns the endpoint's own noise into a coin flip: identical input, publishing on half the runs and not the other half, with nothing in the report saying which run was the odd one out. If the spread straddles the floor you want, the question is the problem rather than the floor, and no value of min_probability makes a boundary-straddling question stable. Sharpen it, name the criterion that separates the cases, and measure again.

What no rules means

With no rules there are no ambient findings. The pass reports no_rules rather than a clean document, so "nothing was inspected" and "nothing was found" are different answers, and that distinction is pinned by verify/rules_test.py and by the negative control in verify/omp_lsp.sh. The chat review does not step in to cover the gap: PROTOCOL.md §12 records that as a decision.

Two negative controls are recorded for the rules harness, and both are meant to be red in a particular way. With the decide endpoint dead, the rules harness reports 0 failures and 4 skips, each naming why, because "no endpoint" must not read as "no product". With the stub alive but answering nothing usable, it reports 4 failures and 1 skip, and nothing in those failures says stub. That is why the runner owns the stub's whole lifecycle, checks the process id as well as the health endpoint, and waits for the port to be free: twice in this project a red harness turned out to be a stale stub, which from the client's end is indistinguishable from a product defect.

The suite also records a defect that passed every test before it was found: diagnosticProvider.workspaceDiagnostics was advertised as true from the first capability block while workspace/diagnostic was never implemented, and Neovim's on_refresh checks that flag. That is what verify/smoke.py now pins. Two further defects were found in the harnesses themselves rather than in the product, and are recorded with the same weight.

07 · Limitations

Known unverified, and known limitations

Kept here because they are boundaries rather than oversights, and because a page that pitches a tool without them is not worth reading. Sources: docs/VERIFICATION.md §10 and §11, and docs/MODEL.md §8.

  • The hosted default decide endpoint has not been called from here. api.typesafe.ai is the default and was never reached. What was called is the same model through a different route, OpenRouter's /alpha/decisions (typesafe/jev-1.13, eight observations at p = 0.82–0.86), so the wire, the body, the parsing and the key name are verified against a real decision endpoint, and the vendor's own base URL and credential are not. A local System One server is likewise unexercised.
  • Model quality on any verb is not proven. The suite proves the pipeline, never the usefulness of a particular model's output, which is measured by the user in the editor.
  • state = "ready" means the contract passed, never that the file still compiles. Nothing in crates/ parses the result of an applied edit, and that is a decision rather than an omission: a structural probe is blind to the failure that prompted it, a parser would be the largest dependency in the repository, and the party that already holds the file is the user's own language server. Measured three times on google/gemini-2.5-flash-lite, the answer replaced one statement with a block header and did not re-indent the body, so the anchor resolved, state = "ready" was reported, and the file no longer parsed. verify/soak.py and verify/real_model.py call ast.parse on the result, and the harness is the only place that question is asked.
  • The post-apply prediction check covers the plan path only. The server materialises the exact post-edit text and publishes a divergence diagnostic when the client's bytes differ, but that comparison is recorded on the jev.apply step path alone. On a resolved code action, which is the commoner way an edit reaches a buffer, no prediction is recorded and nothing is checked.
  • The client's own diagnostics already reach the server and are dropped. The plugin fills CodeActionContext.diagnostics on every code-action request and pushes a versioned document on every change with a 300 ms debounce; the server reads trigger_kind and nothing else of the context. Correlating them is about 30–40 lines, and it is not built.
  • No treesitter scope. Scope resolution is structural, by brace or indentation, with a whole-file fallback. scope_source reports which was used, so the quality is never claimed to be higher than it is.
  • Undo granularity of a client-applied edit is unmeasured. Headless script execution cannot record undo blocks, so the probe was inconclusive. What is verified is the plugin's own path: :Jev undo restores the buffer byte for byte. Plain u remains unmeasured.
  • shutdown with an explicit params member is rejected with -32602 Unexpected params. JSON-RPC 2.0 permits omitting params and does not define a null one, so the rejection is spec-correct, and Neovim is unaffected: it calls rpc.request('shutdown', nil, …) and Lua drops a nil table value, so the member never reaches the wire. A client that sends null sees a failed shutdown and can force-stop the server.
  • A plan needs anchors that exist in an open document. Steps are resolved against the content the server holds and refused as stale when the target has moved, so a greenfield goal has no step to anchor and jev.plan answers that the plan contained no step whose target could be located, rather than inventing files. That is the reason docs/GUIDE.md §8 puts the first step of greenfield work in the shell, until a document exists.
  • `languages.overrides[].verbs` narrows the menu and nothing enforces the complement. A client can invoke any verb through a hand-built action. The server validates the result rather than the request, which is what the version stamp and the anchor rules are for.
  • Rows that cite an unbuilt harness are requirements, not coverage. verify/goldens/ and verify/bench.sh do not exist yet.

One thing that is not a limitation but reads like one: the project checks itself with jev, and over its own crates/**/*.rs the shipped floors produced two findings in 140 candidates. A rules pass on a repository whose conventions are already written down and followed is quiet, and quiet is the intended end state rather than a failure to detect.
